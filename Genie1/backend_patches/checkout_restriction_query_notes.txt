Unprocessed MR-Checkout Restriction:
  frappe_server_scripts/unprocessed_mr_checkout_restriction.py

  frappe_server_scripts/bioman_confirmed_quotation_checkout_restriction.py

The MR query joins to distinct Material Requests with submitted POs rather
than a correlated NOT EXISTS subquery. The ToDo join and its original row
multiplicity/count remain intact. Null workflow states still fail the same
predicate. Half-day/permission exemptions are unchanged.

The project query joins to distinct projects with submitted Sales Orders.
Confirmed quotation rows, grouping, ordering and project/quotation links stay
the same. Draft and cancelled orders do not satisfy either restriction.

MariaDB can materialize and index distinct derived tables for equality joins:
https://mariadb.com/docs/server/ha-and-performance/optimization-and-tuning/query-optimizations/optimizations-for-derived-tables/derived-table-with-key-optimization

These are query-plan candidates, not measured speed fixes. The new plans may
still scan large order tables. Before production rollout, compare original
and replacement SQL with EXPLAIN and measure them on the ERP database; keep
the faster plan only when equivalent results are confirmed. The project's
configured event must be kept; the user's source comment said Before Save,
while the Recorder showed Before Insert. Comments do not configure events.

If plans remain slow, inspect indexes covering:
  ToDo: allocated_to, reference_type, status, reference_name
  Purchase Order Item: parent, material_request
  Purchase Order: docstatus, name
  Project: owner, project_type
  Quotation: custom_project, workflow_state
  Sales Order: docstatus, project
These are candidates, not commands to create every index. Existing indexes,
cardinality, join order and write cost determine which are appropriate.
