GENIE OPPORTUNITIES WEB PAGE — LISTING AND DETAILS ONLY

Files
  opportunities.html: complete combined HTML, internal CSS and internal JavaScript.
  mobile_opportunity_policy.py: existing API with added read visibility actions.
  No external libraries, credentials, API keys, Lead form, or GPS code are included.

ERPNext installation (deploy this before installing the rebuilt APK)
  1. Open Website > Web Page > New.
  2. Title: Opportunities
     Route: genie-opportunities
     Content Type: HTML
     Published: checked
  3. Paste the ENTIRE contents of opportunities.html into the HTML/Main Section.
     Keep its <style> and <script> blocks. Do not paste it into a Server Script.
     If the editor has separate JavaScript/CSS fields, leave those empty when
     using the combined file, so the code is not executed twice.
  4. Save. Use the page's full-width option if available. The page has a scoped,
     full-window root and does not modify the styles of other ERP pages.
  5. Sign in as a normal Opportunity Owner and open:
       https://YOUR-ERP-HOST/genie-opportunities
     The page verifies frappe.auth.get_logged_user without displaying the user email.
     Do not pass a user, SID, token, or password in the URL.
     The API requests use this same ERP origin and its existing session cookie.
  6. If your deployment caches authenticated HTML, exclude this route from shared
     proxy/CDN caching. No Opportunity/user data is stored in this HTML file.

API dependencies - update the existing policy script with this update
  GET /api/method/frappe.auth.get_logged_user
  GET /api/method/mobile_opportunity_policy?action=list
  GET /api/method/mobile_opportunity_policy?action=detail&name=OPPORTUNITY-ID
  GET /api/method/mobile_opportunity_policy?action=count
  GET /api/resource/Opportunity/{name}
  GET /api/method/frappe.desk.form.load.getdoctype?doctype=Opportunity
  GET /api/method/frappe.client.get_value (creator's name, if permitted)
  GET /api/method/mobile_opportunity_policy?action=get
  GET /api/method/mobile_opportunity_policy?action=owner_options
  POST /api/method/mobile_opportunity_policy action=save
  POST /api/method/mobile_opportunity_policy action=change_owner
  POST /api/method/smartflo.api.initiate_call
  GET /app (same-session CSRF bootstrap when the website has no CSRF token)

implemented note audit and owner_options/change_owner actions. Its business

Flutter integration
  opportunities_webview_page.dart is dedicated to this page. It sets the ERP SID
  cookie on the configured SITE_URL host without clearing other WebView cookies.
  It blocks navigation away from this exact ERP route. No shared SessionWebView
  behavior was changed. Home's two Opportunity entry points use this new widget.
  List/detail routing messages only control the native New Lead button and Back.
  All requests and writes stay in the webpage. Native New Lead returns to it and
  refreshes the Opportunity view.

Verification before rollout

  - Compare list owner/filter results to ERP, then test next-page loading.
  - Test all three owner fields separately; an unrelated user must not see the record.
  - A populated higher-priority field assigned to someone else must block fallback.
  - NULL/empty higher-priority fields must fall back to the next populated field.
  - Field-owner-only readers must not gain edit, reassignment or calling access.
  - Edit status with/without the required new note; verify note author/server time.
  - Check follow-up dates and existing Demo/related-document validation.
  - After reassignment, only the first populated owner in the configured priority
    order determines visibility; lower-priority matching fields do not grant access.
  - Use a controlled phone number to verify Smartflo; never retry an uncertain call.
  - In the app, New Lead must open the existing Flutter form, including its existing
    City/Town, District, Location and GPS behavior. No WebView geolocation is used.
  - Verify Android WebView cookies, Back, keyboard, and native return on a device.
